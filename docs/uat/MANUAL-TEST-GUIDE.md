# Gather 手工验收测试指南

> 适用版本：数据库迁移已包含 `0011_fix_test_conclusion_and_construction_summary.sql`
>
> 配套清单：[MANUAL-TEST-CHECKLIST.md](./MANUAL-TEST-CHECKLIST.md)
>
> 操作参考：[用户操作手册](../manual/USER-MANUAL.md)

## 1. 目的与范围

本指南用于在自动化验收通过后进行业务人员手工验收。重点检查真实操作体验、跨角色责任、提示文案、通知、异常路径及视觉一致性，不替代已经执行的 Playwright、TypeScript 和构建检查。

最终自动化基线为：smoke 13 passed、full 23 passed、0 failed、0 skipped。手工验收不得通过降低预期、跳过关键流程或使用非 UAT 业务数据来换取通过。

## 2. 测试人员与职责

建议至少安排一名测试记录人和以下业务身份的实际使用人员；同一自然人可以切换账号，但职责分离用例必须使用不同账号。

| 身份 | 用途 |
|---|---|
| `admin` | 权限、小组、人员、全局管理和异常代办 |
| `manager` | 经理菜单、本人所带小组范围和项目管理 |
| `user` | 普通成员、本人任务和越权验证 |
| 项目负责人 | 项目开发任务审批、内部测试、无需测试、项目完成 |
| 测试组长 | 必须是已标记为测试小组的小组负责人；确认排期、结论和建设成果 |
| 测试工程师 | 登记外部测试、执行测试活动、批次、工时和结论 |
| 自动化测试工程师 | 创建并推进测试建设工作 |

系统角色和业务身份不能互相替代。例如 `manager` 不是某项目负责人时不能审批该项目任务；测试组长也不能因此审批开发任务。

## 3. 环境与数据准备

1. 由环境管理员提供测试站点入口和测试账号，测试文档中只记录账号代号，不记录邮箱、密码或任何认证信息。
2. 开始前确认版本包含迁移 `0011`，并记录测试日期、版本号或构建标识。
3. 查询并优先复用已有 `UAT-质量保障组`、`UAT-研发组` 等数据，禁止盲目重复创建。
4. 新建数据统一使用 `UAT-手工-日期-场景` 命名，例如 `UAT-手工-0813-审批项目`。
5. 准备一个测试小组并指定测试组长；准备测试工程师、自动化测试工程师、项目负责人、普通任务负责人。
6. 准备一条可完整流转的 UAT 项目及两条开发任务，分别验证批准和驳回。
7. 准备内部项目测试候选数据：项目负责人名下至少一条已审批且尚未被通过轮次覆盖的开发任务。
8. 不删除任何非 `UAT-` 数据。本轮默认不清理 UAT 数据，以保留审计证据；确需清理由环境负责人另行审批并先导出清单。

## 4. 安全要求

- 不在清单、缺陷单、聊天、截图、录像或文件名中记录真实密码、Token、Cookie、JWT、anon key、Authorization 请求头或内部密钥。
- 截图前清空登录输入框，裁掉地址栏、浏览器收藏、通知中的真实个人信息和其他应用窗口。
- 只操作本轮明确创建或确认可用的 `UAT-` 数据，不使用真实项目验证删除、越权或异常流程。
- 不通过浏览器开发者工具复制认证请求，不用管理员账号代替普通账号验证 RLS。
- 若发现疑似敏感信息泄露，停止传播证据，通知环境管理员删除附件并轮换相关凭据。

## 5. 推荐执行顺序

1. **P0 入口与身份**：登录、退出、错误凭据、三系统角色菜单与路由。
2. **P0 基础关系**：人员、小组、测试小组、项目负责人和各职位身份。
3. **P0 任务闭环**：创建、开始、挂起、继续、工时、提交、批准、驳回、越权。
4. **P0 测试中心闭环**：内部/外部测试、排期、活动、批次、结论退回与确认。
5. **P0 测试建设**：创建、排期、拆分、进度、工时、成果确认和汇总一致性。
6. **P1 扩展流程**：无需测试、资源汇总、通知、项目完成与异常代办。
7. **P1/P2 UI 与体验**：日期控件、弹窗、中文类型、工时口径、主题和提示文案。
8. 执行完毕后复核所有 P0、统计缺陷、形成签字结论。

建议每个跨角色流程使用唯一数据串行执行，状态交接时立即截图，避免多人同时修改同一记录。

## 6. 自动化与手工测试分工

清单中的“覆盖”标记含义：

- **自动化+手工**：自动化已验证关键状态或权限；手工仍需确认文案、体验、责任人和页面数据一致性。
- **手工重点**：依赖人的视觉、业务判断、通知阅读或不可预测异常，必须人工执行。
- **自动化证据可复用**：若时间受限，可引用最终 HTML 报告，但清单中标记为 P0 的“手工重点”不得省略。

## 7. 证据留存

每条用例至少填写实际结果和通过状态。P0 用例、失败用例及关键状态交接必须留证据。

建议证据命名：`用例ID-日期-序号.png`，例如 `TASK-06-0813-01.png`。证据只包含 UAT 虚构数据。可接受的证据包括：

- 脱敏截图；
- HTML 报告相对路径；
- 不含认证信息的错误码和业务错误提示；
- UAT 数据名称、状态和审计时间；
- 测试人员签字或缺陷单编号。

## 8. 缺陷记录规范

缺陷标题格式：`[Gather][模块][严重级别] 简要现象`。

每条缺陷必须包含：

1. 缺陷编号、发现日期、发现人、环境版本。
2. 对应用例 ID、角色代号和 UAT 数据名称。
3. 前置状态、可重复步骤、实际结果、预期结果。
4. 发生频率和是否重试；禁止用无限等待掩盖网络或产品缺陷。
5. 脱敏截图或录像、控制台业务错误码（如有）。
6. 严重级别：
   - **阻塞/P0**：无法登录、权限越权、核心状态机无法完成、数据错误或安全泄露。
   - **严重/P1**：重要功能错误但有受控绕行方式，或关键汇总明显不一致。
   - **一般/P2**：局部校验、通知、文案或体验问题。
   - **建议/P3**：不影响使用的优化建议。

发现缺陷后先保留现场，不擅自修改业务代码或数据库。测试脚手架问题与产品缺陷分开记录。

## 9. 暂停与恢复条件

出现以下情况应暂停相关模块：环境不可达超过约定窗口、账号关系配置错误、P0 数据被他人修改、疑似权限泄露、敏感信息进入证据、核心状态机产生不可逆异常。

恢复时记录环境恢复时间和处理人，从最近一个已确认状态重新执行；不得直接把失败步骤标为通过。

## 10. 通过门槛与上线建议

手工验收通过必须同时满足：

- 所有 P0 用例执行且通过，0 skipped；
- P1 用例无未关闭的阻塞或严重缺陷；
- 无权限越权、非 UAT 数据误操作或敏感信息泄露；
- 任务、测试结论、测试建设及工时汇总的数据库状态与页面一致；
- smoke 13/13、full 23/23 的最终自动化基线仍有效；若产品或环境再次变更，应重新运行；
- 测试负责人和业务负责人完成签字结论。

允许带病上线只适用于已评估的 P2/P3 缺陷，必须记录负责人、修复计划和复验时间。任何 P0/P1 权限、状态机或数据一致性缺陷均阻塞上线。
