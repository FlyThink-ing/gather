## 1. 使用前必读

Gather 用于管理研发项目、开发任务、项目审批，以及内部项目测试、外部独立测试和测试建设工作。

使用时请遵守以下原则：

1. 以页面实际显示的按钮为准。按钮不可见时，通常是当前角色、业务身份或数据状态不满足条件。
2. 开发任务在“任务管理”处理；新测试活动和测试建设任务必须进入“测试中心”处理。
3. 所有项目开发任务均由该项目的“项目负责人”逐项审批。小组组长、部门经理不会仅凭身份自动获得审批权。
4. 测试排期、无需测试申请和最终测试结论由“测试小组组长”确认。
5. 禅道仍是测试用例和 Bug 明细的唯一来源。Gather 只保存轮次汇总和禅道链接。
6. 不要在任务描述、评论、链接、截图或文档中填写密码、Token、Cookie、JWT、私钥等敏感信息。

### 1.1 状态颜色提示

- 蓝色通常表示进行中。
- 青色通常表示测试中。
- 琥珀色通常表示待审核或待确认。
- 绿色通常表示完成或通过。
- 红色通常表示失败或错误。
- 橙色表示时间风险，例如已逾期或延期完成。
- 紫色表示挂起。

## 2. 角色、身份与权限

### 2.1 系统角色与业务身份的区别

“系统角色”控制菜单和通用管理能力；“业务身份/关系”来自具体数据关系，控制某个项目或测试流程中的责任。两者不能互相替代。

| 类别 | 名称 | 如何获得 | 主要作用 |
| --- | --- | --- | --- |
| 系统角色 | 管理员 `admin` | 管理员在“权限管理”分配 | 全局管理、异常代办、管理用户角色和小组 |
| 系统角色 | 组长/经理 `manager` | 管理员在“权限管理”分配 | 管理授权范围内的数据、查看数据分析 |
| 系统角色 | 普通用户 `user` | 注册默认角色或管理员分配 | 查看授权数据、管理自己负责的任务 |
| 业务身份 | 项目负责人 | 在项目的“项目负责人”字段指定 | 审批本项目全部开发任务；发起内部项目测试；申请无需测试；完成项目 |
| 业务身份 | 小组组长 | 在“小组管理”的“组长”字段指定 | 形成小组管理关系；经理可据此创建归属项目 |
| 业务身份 | 测试组长 | 同时是标记为“测试小组”的组长 | 确认测试排期、拆分测试活动、确认测试结论、确认无需测试、确认测试建设成果 |
| 业务身份 | 主测试负责人 | 测试组长在确认排期时指定 | 开始/暂停/恢复测试、记录批次和工时、提交结构化结论 |
| 职位身份 | 测试工程师 | 开发人员档案中的职位 | 可登记外部独立测试，可被分配测试活动 |
| 职位身份 | 自动化测试工程师 | 开发人员档案中的职位 | 具备测试工程师能力，并可新建测试建设工作 |
| 业务关系 | 建设工作负责人/任务负责人 | 创建或拆分建设工作时指定 | 推进建设工作、更新本人建设任务、登记工时、提交成果 |

> 例：一名普通用户可以是项目负责人，因此能审批该项目任务；一名 `manager` 如果不是项目负责人，则不能审批该项目任务。测试组长也不会自动取得项目任务审批权。

### 2.2 各角色建议工作入口

- 管理员：权限管理、小组管理、开发人员、项目管理、任务管理、测试中心、数据分析。
- 部门经理/manager：项目管理、开发人员、任务管理、数据分析；创建项目还要求本人担任至少一个小组组长。
- 项目负责人：项目全景、任务管理、测试中心。
- 小组组长：小组协作相关项目和任务；若同时是 `manager`，可创建归属本人所带小组的项目。
- 普通成员：工作台、任务管理、项目管理只读视图。
- 测试组长：测试中心的待排期、活动拆分、待确认结论、无需测试申请和测试建设。
- 测试工程师：测试中心的外部测试登记、本人参与的测试计划、执行批次和工时。
- 自动化测试工程师：测试工程师入口，以及“测试建设”中的“新建建设工作”。

## 3. 新员工 30 分钟快速入门

### 3.1 第 0～5 分钟：登录并确认身份

**适用角色**：所有用户。

**前置条件**：已有账号；正式环境中账号已完成邮箱验证。

**操作步骤**：

1. 打开 Gather 登录页。
2. 输入“邮箱”和“密码”，点击“登录”。
3. 进入系统后查看左下角姓名和角色。
4. 打开“开发人员”，确认自己的姓名、职位和账号状态正确。

**预期结果**：进入“项目概览”，侧边栏只显示当前角色可访问的菜单。

**注意事项**：若页面顶部显示“演示模式”，当前数据仅保存在浏览器本地，不应当作正式业务数据。

### 3.2 第 5～15 分钟：认识工作台与任务

**适用角色**：所有用户。

**前置条件**：已登录。

**操作步骤**：

1. 在“工作台”查看总任务、进行中、测试中、待我审批、已完成、延期完成和逾期数量；点击卡片会带入同口径的任务预设。
2. 查看甘特图，理解计划周期与实际投入。
3. 打开“任务管理”，点击“我的任务”。
4. 使用搜索框或项目、状态、优先级、小组、人员等筛选条件定位任务。
5. 点击任务标题或“查看详情”图标查看完整信息。

**预期结果**：能找到本人负责的任务并识别当前状态、截止日期和下一步操作。

**注意事项**：普通用户默认只看本人任务；经理默认看本人小组范围；管理员可看全部范围。

### 3.3 第 15～25 分钟：完成一次任务流转

**适用角色**：普通成员、项目负责人、manager、管理员。

**前置条件**：本人有一条“待处理”的开发任务；项目负责人已配置。

**操作步骤**：

1. 在任务行点击“开始”，状态变为“进行中”，系统开始累计实际工时。
2. 若被其他工作打断，点击“挂起（被其他任务打断时）”并确认；恢复时点击“继续”。
3. 完成工作后点击“完成并提交审批”。逾期时按提示填写延期原因。
4. 项目负责人可从“待我审批”入口核对“任务详情”，选择“审批通过”或“审批驳回”。组长如需改派、调整日期或优先级，使用独立的“本组任务管理”入口并填写原因，不能代替负责人执行任务。

**预期结果**：通过后状态为“已完成”或“延期完成”；驳回后回到“进行中”。

**注意事项**：进入“审核中”后任务不可编辑；管理员代办必须填写异常原因并留下审计记录。

### 3.4 第 25～30 分钟：查看项目与通知

**适用角色**：所有用户。

**前置条件**：已登录。

**操作步骤**：

1. 打开“项目管理”，进入相关项目的“项目全景”。
2. 查看项目概览、测试与质量、人员与投入、阶段时间线。
3. 点击页面右上角铃铛查看通知；需要时点击“全部已读”。

**预期结果**：能从项目全景跳转到统一任务入口，并知道通知中的待办来源。

**注意事项**：统计卡片用于判断风险；具体处理仍应进入任务或测试计划详情。

## 4. 登录、退出与页面导航

### 4.1 登录或注册

**适用角色**：所有用户。

**前置条件**：能访问 Gather；注册是否开放由组织管理规则决定。

**操作步骤**：

1. 登录：填写必填的“邮箱”“密码”（至少 6 位），点击“登录”。
2. 注册：点击“注册”，填写必填的“邮箱”“密码”“姓名”，选择“职位”，再点击“注册”。
3. 正式环境提示“注册成功，请前往邮箱完成验证后再登录。”时，先完成邮箱验证。

**预期结果**：成功后进入“项目概览”。

**注意事项**：演示模式允许任意邮箱和密码登录，仅用于体验。登录页当前没有“忘记密码”按钮，如需重置密码请联系管理员。

### 4.2 退出登录

**适用角色**：所有用户。

**前置条件**：已登录。

**操作步骤**：在左侧栏底部点击“退出登录”。

**预期结果**：返回登录页；再次访问受保护页面会被重定向至登录页。

**注意事项**：在共享电脑上使用完毕务必退出登录。

### 4.3 导航与主题

**适用角色**：所有用户。

**前置条件**：已登录。

**操作步骤**：

1. 从侧边栏进入“工作台”“项目管理”“开发人员”“任务管理”“测试中心”。
2. 管理员还可进入“小组管理”“数据分析”“权限管理”；manager 可进入“数据分析”。
3. 点击顶部太阳/月亮图标切换白天或黑夜模式。
4. 点击顶部铃铛打开通知。

**预期结果**：菜单随角色显示；无权限路由会返回工作台。

**注意事项**：前端隐藏菜单只是操作提示，最终权限仍由服务端校验。

## 5. 开发人员与小组

### 5.1 添加或维护开发人员

**适用角色**：管理员、manager；停用、启用和删除仅管理员。

**前置条件**：已登录并具备相应系统角色。

**操作步骤**：

1. 打开“开发人员”，点击“添加人员”。
2. 填写必填“姓名”，选择“职位”，点击“保存”。
3. 在人员行使用“编辑”维护信息。
4. 管理员可执行停用、启用或删除；按确认提示核对影响。

**预期结果**：人员出现在列表，页面显示所属小组、未完成任务、负载、账号和状态。

**注意事项**：停用后该人员不再出现在任务分配和甘特图中，但历史数据保留。删除前必须先处理其项目负责人等受限关系。

### 5.2 创建小组并维护成员

**适用角色**：管理员。

**前置条件**：开发人员档案已建立。

**操作步骤**：

1. 打开“小组管理”，点击“创建小组”。
2. 填写必填“小组名称”，按需选择“组长”。
3. 若该组承担测试管理，勾选“标记为测试小组”。
4. 点击“保存”。
5. 在小组卡片点击添加成员入口，选择开发人员并点击“添加”。
6. 需要时使用“编辑小组/更换组长”或“移出小组”。

**预期结果**：小组显示组长、成员和“测试小组”标识；组长自动作为小组成员。

**注意事项**：同一人员可跨组；系统会提示其已在其他小组，请人工评估负载。更换组长不会转移项目负责人或待审批任务。删除小组前应先迁移关联项目；若页面提示与数据库限制冲突，以服务端拒绝为准。

### 5.3 调整系统角色

**适用角色**：管理员。

**前置条件**：目标用户已注册并具有人事档案。

**操作步骤**：

1. 打开“权限管理”。
2. 在目标用户的“调整角色”下拉框选择“管理员”“组长”或“普通用户”。
3. 若降低自己的权限，阅读二次确认后再继续。

**预期结果**：目标用户的菜单和通用权限按新角色生效。

**注意事项**：调整系统角色不会自动变更项目负责人、小组组长、测试组长或主测试负责人等业务关系。

## 6. 项目创建与生命周期

### 6.1 创建项目

**适用角色**：管理员、manager。

**前置条件**：至少已有一个小组和一个可用项目负责人；manager 必须担任至少一个小组组长。

**操作步骤**：

1. 打开“项目管理”，点击“添加项目”。
2. 填写必填“项目名称”“所属小组”“项目负责人”。
3. 按需填写“计划开始”“计划结束”和“描述”。新项目创建后默认为“进行中”。
4. 点击“保存”。

**预期结果**：项目卡片出现，并展示任务进度、周期、投入、质量与风险指标。

**注意事项**：manager 只有一个所带小组时系统自动带入；有多个时必须选择。项目负责人是本项目开发任务的唯一日常审批人。

### 6.2 编辑、暂停或重新打开项目

**适用角色**：项目负责人；管理员仅可走异常代办并填写原因。小组归属和负责人调整由管理员或符合范围的组长走独立治理入口。

**前置条件**：项目存在；目标小组和负责人有效。

**操作步骤**：

1. 项目负责人在项目卡片点击“编辑”，只修改名称、描述和计划日期。
2. 如需变更所属小组或项目负责人，点击“调整归属与负责人”，填写原因后确认；状态使用暂停、恢复或完成项目的专用操作。
3. 管理员代改业务字段时必须填写异常原因；普通编辑不会修改治理字段或状态。

**预期结果**：业务字段或治理字段按对应专用流程更新，并保留原因审计。

**注意事项**：历史审批人不会被改写。完成项目应使用独立“完成项目”操作，不要仅修改状态。

### 6.3 完成项目

**适用角色**：项目负责人；管理员仅作异常代办。

**前置条件**：项目未完成；开发任务、测试工作、待审批任务、活动轮次及测试门禁均已处理。

**操作步骤**：

1. 在项目卡片或“项目全景”点击“完成项目”。
2. 系统检查阻断项。
3. 无阻断时确认完成。
4. 仅管理员可在确有异常时填写必填“强制完成原因”，点击“确认强制完成”。

**预期结果**：项目状态变为“已完成”，完成时间和状态审计被记录。

**注意事项**：管理员强制完成会绕过正常阻断，应仅用于负责人离职、系统异常等场景。已完成或已暂停项目不能发起新的内部测试。

### 6.4 项目异常数据处置

项目管理不提供直接删除入口。异常数据处置需等待后续具备审计记录的专用流程；当前请使用暂停、恢复、完成或治理调整等已有操作，避免直接破坏关联任务和历史记录。

## 7. 任务创建、工时与审批

### 7.1 创建开发任务

**适用角色**：管理员、manager、普通用户。

**前置条件**：至少有一个“进行中”项目；项目已配置负责人。

**操作步骤**：

1. 打开“任务管理”，点击“添加任务”。
2. 填写必填“任务标题”“所属项目”“开始日期”“截止日期”。
3. 选择“负责人”和“优先级”，按需填写“描述”。
4. 点击“保存”。

**预期结果**：创建“待处理”的开发任务，所属小组自动继承项目。

**注意事项**：普通用户的负责人锁定为本人；负责人允许暂时“未分配”，但这会形成项目风险。截止日期不能早于开始日期。新测试任务不能从此入口手工创建。

### 7.2 开始、挂起、继续与实际工时

**适用角色**：任务负责人、管理员、manager。

**前置条件**：开发任务状态为“待处理”“进行中”或“已挂起”。

**操作步骤**：

1. “待处理”任务点击“开始”，进入“进行中”。
2. 工作被打断时点击“挂起（被其他任务打断时）”，再点击“确认挂起”。
3. 恢复工作时点击“继续”。

**预期结果**：进入“进行中”时开启工时段；离开“进行中”时关闭工时段；挂起期间不累计工时。

**注意事项**：普通开发任务的实际工时由状态流转自动累计，不需要手工填写。页面“实际投入”是已关闭工时段之和。

### 7.3 提交审核

**适用角色**：任务负责人、管理员、manager。

**前置条件**：开发任务处于“进行中”，项目负责人有效。

**操作步骤**：

1. 点击“完成并提交审批”。
2. 在“确认提交审批”弹窗核对项目负责人。
3. 若已超过截止日期，填写必填“延期原因”。
4. 点击“确认提交审批”。

**预期结果**：任务进入“审核中”，记录实际提交时间；项目负责人收到待办通知。

**注意事项**：提交时间代表工作实际完成时刻；最终完成时间在审批通过时确认。审核中任务不可编辑。

### 7.4 审批通过或驳回

**适用角色**：该项目负责人；管理员仅异常代办。

**前置条件**：任务处于“审核中”。

**操作步骤**：

1. 点击任务标题或“查看详情”，核对负责人、日期、描述、实际投入和延期说明。
2. 通过：点击“审批通过（需确认详情）”，再点击“确认审批并完成任务”。
3. 驳回：点击“审批驳回”，填写必填“驳回原因”，点击“确认审批驳回”。
4. 管理员代办时，额外填写必填“管理员代办原因”。

**预期结果**：通过后按是否逾期进入“已完成”或“延期完成”；驳回后回到“进行中”，负责人可修改后重提。

**注意事项**：小组组长、manager 或测试组长身份本身均不产生审批权。管理员代办会留下不可变审计记录。

### 7.5 任务状态与责任人

| 当前状态 | 可执行动作 | 下一状态 | 主要责任人 |
| --- | --- | --- | --- |
| 待处理 | 开始 | 进行中 | 任务负责人；管理员/manager 可协助 |
| 进行中 | 挂起 | 已挂起 | 任务负责人；管理员/manager 可协助 |
| 已挂起 | 继续 | 进行中 | 任务负责人；管理员/manager 可协助 |
| 进行中 | 完成并提交审批 | 审核中 | 任务负责人；管理员/manager 可协助 |
| 审核中 | 审批通过 | 已完成/延期完成 | 项目负责人 |
| 审核中 | 审批驳回 | 进行中 | 项目负责人 |
| 审核中 | 异常代办通过/驳回 | 已完成、延期完成或进行中 | 管理员，必须填写代办原因 |
| 已完成/延期完成 | 无常规编辑 | 终态 | 只读 |

### 7.6 查看与筛选任务

任务管理不提供直接删除入口。异常任务处置需等待后续专用审计流程；请勿以删除替代状态流转、改派或归档管理。

**适用角色**：所有用户查看；管理员/manager 可删除开发任务。

**前置条件**：已登录。

**操作步骤**：

1. 使用“我的任务”等范围按钮和搜索、状态、优先级、项目、小组、人员筛选。
2. 点击任务标题查看详情和关联测试记录。
3. 管理员或 manager 可点击“删除”并确认。

**预期结果**：列表按服务端数据范围分页返回；从项目全景进入时会保留 URL 筛选条件。

**注意事项**：测试活动任务应点击“测试中心处理”；测试建设任务应点击“建设工作处理”；历史单任务测试只读保留。

## 8. 测试中心总览

测试中心包含三个页签：

- “测试计划”：内部项目测试和外部独立测试。
- “测试建设”：自动化框架、脚本、工具、环境、数据、平台等持续建设。
- “资源汇总”：按人汇总三类来源的计划与实际工时及并发冲突。

### 8.1 进入测试中心

**适用角色**：所有已登录用户；可见数据受业务关系和服务端权限限制。

**前置条件**：账号已绑定开发人员档案。

**操作步骤**：点击侧边栏“测试中心”，在“测试计划”“测试建设”“资源汇总”间切换，需要时点击“刷新”。

**预期结果**：显示本人有权查看的计划、建设工作和资源数据。

**注意事项**：若提示“尚未配置测试小组”，管理员必须先在“小组管理”完成配置。

## 9. 内部项目与外部独立测试

### 9.1 发起内部项目测试

**适用角色**：项目负责人。

**前置条件**：项目为“进行中”；尚未批准无需测试；没有未结束轮次；至少有一条“已完成”或“延期完成”且未被通过轮次覆盖的开发任务。

**操作步骤**：

1. 从“项目全景”的测试与质量区域点击“发起项目测试”，或进入“测试中心”点击“发起内部测试”。
2. 填写必填“测试计划名称”“测试小组”“内部项目”“测试范围”“测试目标”。
3. 按需填写“阶段 / 版本”“优先级”“期望开始”“期望结束”“建议主测”“环境说明”“预期交付物”“相关链接”“禅道链接”。
4. 勾选本轮要求的报告。
5. 点击“提交测试申请”。

**预期结果**：生成第 1 轮测试，状态为“待确认排期”；系统自动快照尚未被通过轮次覆盖的已审批开发任务。

**注意事项**：“内部项目”下拉只显示本人负责且当前可发起测试的项目。管理员也不能替项目负责人发起内部测试。

### 9.2 登记外部独立测试

**适用角色**：测试工程师、自动化测试工程师、管理员。

**前置条件**：已配置测试小组；账号职位正确。

**操作步骤**：

1. 在“测试中心 > 测试计划”点击“登记外部测试”。
2. 填写必填“测试计划名称”“测试小组”“外部项目名称”“项目负责人（文本）”“测试范围”“测试目标”。
3. 按需填写其他计划字段并选择报告要求。
4. 点击“提交测试申请”。

**预期结果**：生成外部独立测试计划和“待确认排期”的首轮测试。

**注意事项**：外部项目负责人只保存文本，不要求对方登录系统；不要在字段中填写外部账号或敏感联系信息。

### 9.3 发起下一轮测试

**适用角色**：内部项目由项目负责人；外部测试由测试人员；管理员具备异常处理能力。

**前置条件**：上一轮为“测试通过”“测试不通过”或“已取消”，且当前没有未结束轮次。

**操作步骤**：

1. 打开测试计划详情，点击“发起下一轮”。
2. 填写必填“阶段 / 版本”。
3. 点击“创建新一轮”。

**预期结果**：新轮次进入“待确认排期”。内部项目仅纳入新增的已审批、未被通过轮次覆盖的开发任务。

**注意事项**：若系统提示没有新增可纳入任务，应先完成并审批新的开发任务。

## 10. 测试排期、活动、批次与结论

### 10.1 确认或退回测试排期

**适用角色**：测试组长；管理员可异常处理。

**前置条件**：轮次状态为“待确认排期”或“已退回”；主测候选为在职测试工程师或自动化测试工程师。

**操作步骤**：

1. 打开测试计划详情。
2. 确认：点击“确认排期”，填写必填“主测试负责人”“计划开始”“计划结束”，按需填写“排期说明”，再点击“确认并分配”。
3. 退回：点击“退回申请”，填写必填“原因”并确认。

**预期结果**：确认后状态为“待开始”；退回后状态为“已退回”。

**注意事项**：计划结束不能早于计划开始。建议主测仅供参考，最终由测试组长确认。

### 10.2 拆分测试活动

**适用角色**：测试组长；管理员可异常处理。

**前置条件**：排期已确认；轮次为“待开始”“测试中”或“已暂停”。

**操作步骤**：

1. 在计划详情点击“拆分活动”。
2. 填写必填“活动名称”“类型”“负责人”“开始”“结束”“计划工时”。
3. 按需填写“前置条件”“预期交付物”。
4. 点击“创建活动任务”。

**预期结果**：生成测试活动，并同步生成只能在测试中心处理的活动任务。

**注意事项**：类型可选冒烟、系统、回归、性能、兼容性、安全或其他；计划工时必须大于 0。

### 10.3 开始、暂停、恢复或取消轮次

**适用角色**：主测试负责人、测试组长；管理员可异常处理。

**前置条件**：轮次状态允许相应操作。

**操作步骤**：

1. “待开始”点击“开始测试”，进入“测试中”。
2. 需要暂停时点击“暂停”，填写必填原因。
3. “已暂停”点击“恢复”。
4. 需要终止时点击“取消轮次”，填写必填原因。

**预期结果**：轮次按操作进入“测试中”“已暂停”或“已取消”。

**注意事项**：取消是终止性操作；需继续时应发起下一轮。

### 10.4 登记测试活动工时

**适用角色**：轮次参与人、主测试负责人、测试组长；实际权限以页面按钮和服务端校验为准。

**前置条件**：活动已生成任务；用户有权操作该轮次。

**操作步骤**：

1. 在“测试活动与资源”找到活动，点击“登记工时”。
2. 选择“日期”，填写“工时”，按需填写“说明”。
3. 点击“保存工时”。

**预期结果**：活动实际工时和资源汇总同步更新。

**注意事项**：单次登记必须大于 0 且不超过 24 小时，支持 0.5 小时步进。不要从普通任务列表修改测试活动任务。

### 10.5 记录执行批次

**适用角色**：本轮测试参与人。

**前置条件**：轮次为“测试中”。

**操作步骤**：

1. 点击“记录执行批次”。
2. 填写必填“执行日期”“测试类型”“环境”“构建 / 版本”。
3. 可选择“测试活动”；冒烟测试还必须选择“冒烟结果”。
4. 填写计划、实际执行、通过、失败、阻塞、跳过、新增 Bug、Reopen 数量。
5. 按需填写问题、阻断、风险摘要和禅道链接。
6. 点击“保存执行批次”。

**预期结果**：批次进入轮次详情，数量汇总同步更新。

**注意事项**：必须满足“通过 + 失败 + 阻塞 + 跳过 = 实际执行”；所有数量为非负整数；禅道链接需为有效 HTTP/HTTPS 地址。

### 10.6 更新报告状态

**适用角色**：主测试负责人、测试组长；管理员可异常处理。

**前置条件**：计划创建时已选择报告要求。

**操作步骤**：

1. 在“报告出具状态”找到报告。
2. 已完成报告时点击“已出具”。
3. 不出具时点击“未出具”，填写必填“未出具原因”并确认。

**预期结果**：报告状态被记录；所有必需报告处理后方可提交结论。

**注意事项**：Gather 不上传或关联报告文件，只记录是否出具及原因。

### 10.7 提交结构化测试结论

**适用角色**：主测试负责人；管理员可异常处理。

**前置条件**：轮次为“测试中”；必需报告均已处理。

**操作步骤**：

1. 点击“提交结构化结论”。
2. 选择必填“建议结论”：通过或不通过。
3. 必填“实际测试范围”“完成情况”“本轮新问题”“遗留问题”“阻断项”“风险”“发布建议”；没有内容时应明确填写“无”，不能留空。
4. 内部项目选择“不通过”时，还必须选择同项目的“具体整改任务”。
5. 点击“提交给测试组长确认”。

**预期结果**：轮次进入“结论待确认”，测试组长收到待办。

**注意事项**：不通过只关联具体整改任务，不会批量打回全部开发任务。

### 10.8 确认或退回测试结论

**适用角色**：测试组长；管理员可异常处理。

**前置条件**：轮次为“结论待确认”。

**操作步骤**：

1. 核对执行批次、工时、报告状态和结构化结论。
2. 同意时点击“确认结论”。
3. 需修改时点击“退回修改”，填写必填原因并确认。

**预期结果**：确认后按建议结论进入“测试通过”或“测试不通过”；退回后回到“测试中”，主测修改后重新提交。内部项目通过后项目测试门禁变为通过；不通过后进入整改状态。

**注意事项**：结论确认后，本轮测试活动自动完成。数据库必须已执行 `0011` 迁移，否则历史版本可能在最终确认时报状态约束错误。

### 10.9 测试轮次状态与责任人

| 当前状态 | 动作 | 下一状态 | 主要责任人 |
| --- | --- | --- | --- |
| 待确认排期 | 确认排期 | 待开始 | 测试组长 |
| 待确认排期 | 退回申请 | 已退回 | 测试组长，必填原因 |
| 已退回 | 重新确认排期 | 待开始 | 测试组长 |
| 待开始 | 开始测试 | 测试中 | 主测试负责人/测试组长 |
| 测试中 | 暂停 | 已暂停 | 主测试负责人/测试组长，必填原因 |
| 已暂停 | 恢复 | 测试中 | 主测试负责人/测试组长 |
| 测试中 | 提交结构化结论 | 结论待确认 | 主测试负责人 |
| 结论待确认 | 退回修改 | 测试中 | 测试组长，必填原因 |
| 结论待确认 | 确认结论 | 测试通过/测试不通过 | 测试组长 |
| 非终态 | 取消轮次 | 已取消 | 主测试负责人/测试组长，必填原因 |
| 测试通过/测试不通过/已取消 | 发起下一轮 | 待确认排期 | 内部项目负责人或外部测试人员 |

## 11. 无需测试申请

### 11.1 提交或撤回申请

**适用角色**：项目负责人；管理员可异常处理。

**前置条件**：项目尚未完成测试门禁处理。

**操作步骤**：

1. 打开“项目全景”的“测试与质量”。
2. 点击“申请无需测试”。
3. 填写必填“无需测试原因”（10～1000 字），按需填写“关联链接（选填）”。
4. 提交申请。
5. 测试组长处理前，项目负责人可点击“撤回无需测试申请”。

**预期结果**：申请进入待确认；批准前项目仍视为需要测试。

**注意事项**：关联链接必须以 `http://` 或 `https://` 开头。申请不能直接解除测试门禁。

### 11.2 批准或退回申请

**适用角色**：测试组长；管理员可异常处理。

**前置条件**：测试中心显示“无需测试申请待确认”。

**操作步骤**：

1. 在“测试中心 > 测试计划”查看待确认申请，必要时点击“查看项目”。
2. 同意时点击“批准无需测试”。
3. 不同意时点击“退回”，填写必填“退回原因”，再点击“确认退回”。

**预期结果**：批准后项目状态显示“无需测试已批准”，测试门禁解除；退回后项目负责人看到退回原因，可修改方案或发起测试。

**注意事项**：所有提交、撤回、批准和退回均保留审计。

## 12. 测试建设

### 12.1 新建测试建设工作

**适用角色**：自动化测试工程师、测试组长、管理员。

**前置条件**：账号职位或测试组长关系正确；已有可选测试人员。

**操作步骤**：

1. 打开“测试中心 > 测试建设”，点击“新建建设工作”。
2. 填写必填“标题”“负责人”“建设目标”“预期成果”“成果确认标准”。
3. 选择“类型”“优先级”，填写计划日期和“代码库 / 文档 / 流水线链接”。
4. 点击“创建草稿”。

**预期结果**：创建状态为“草稿”的测试建设工作。

**注意事项**：建设工作不关联项目或测试计划，不采集用例、Bug、Reopen，也不计入项目测试成本。

### 12.2 提交并确认排期

**适用角色**：建设负责人提交；测试组长确认；管理员可异常处理。

**前置条件**：建设工作为“草稿”。

**操作步骤**：

1. 建设负责人打开详情，点击“提交排期确认”。
2. 测试组长打开该工作，点击“确认排期与资源”。

**预期结果**：状态依次变为“排期待确认”“进行中”。

**注意事项**：只有进入“进行中”或“已暂停”后，建设任务才能更新执行状态和进度。

### 12.3 拆分任务、更新进度与登记工时

**适用角色**：建设负责人、测试组长可拆分；任务负责人可更新本人任务；管理员可异常处理。

**前置条件**：建设工作允许拆分，负责人为测试工程师或自动化测试工程师。

**操作步骤**：

1. 点击“拆分任务”，填写必填“任务标题”“负责人”，按需填写开始、结束和计划工时，点击“创建任务”。
2. 进入执行阶段后，任务负责人点击“更新进度”，填写 0～100 的“完成进度”，点击“保存进度”。
3. 完成时点击“完成”，或把状态/进度更新至完成。
4. 任务负责人点击“登记工时”，填写日期、0～24 小时内的工时和说明，点击“保存工时”。点击“工时明细”可查看记录；普通人员仅可在允许状态下编辑或作废本人的手工记录，且必须填写原因；自动记录对普通人员只读，测试组长或管理员可填写原因后进行审计修正。

**预期结果**：建设任务进度、状态、计划工时和实际工时同步到详情及资源汇总。

**注意事项**：测试建设任务必须从建设详情处理，不要在普通任务列表直接修改。

### 12.4 暂停、恢复、提交与确认成果

**适用角色**：建设负责人推进；测试组长确认成果；管理员可异常处理。

**前置条件**：建设工作处于相应可操作状态。

**操作步骤**：

1. 需要中止时点击“暂停”，填写说明；继续时点击“恢复”。
2. 建设负责人完成工作后点击“提交成果确认”，填写成果说明。
3. 测试组长核对后点击“确认最终成果”；需完善时点击“退回完善”并填写原因。
4. 测试组长需要终止工作时点击“取消”并填写原因。

**预期结果**：成果确认后状态为“已完成”，未取消的子任务统一完成；退回后回到“进行中”。

**注意事项**：暂停、取消、提交成果和退回均要求说明，并进入状态与成果审计。

## 15. 测试中心完整示例

以下示例使用虚构名称，不对应真实人员或项目。

### 15.1 示例：内部项目“示例订单平台 V3”

**适用角色**：项目负责人、测试组长、主测试负责人、测试活动负责人。

**前置条件**：项目为“进行中”；开发任务 A、B 已审批完成；已配置“示例质量组”和组长。

**操作步骤**：

1. 项目负责人发起内部测试：计划名称“示例订单平台 V3 验收”，阶段/版本“V3.0”，范围填写“订单创建、支付回调、退款主流程”，目标填写“验证 V3.0 可发布性”，选择“示例质量组”和系统测试报告。
2. 状态：未发起测试 → 待确认排期。责任从项目负责人转给测试组长。
3. 测试组长确认主测、计划日期，并拆分“冒烟验证”“系统回归”两个活动。
4. 状态：待确认排期 → 待开始。责任转给主测试负责人及活动负责人。
5. 主测点击“开始测试”；活动负责人分别登记工时。
6. 记录执行批次：计划 30、实际 30、通过 26、失败 2、阻塞 1、跳过 1；新增 Bug 2、Reopen 0。四类结果数量合计必须为 30。
7. 报告完成后点击“已出具”。
8. 若结论为不通过，主测选择具体整改任务，完整填写七项结论后提交。
9. 测试组长核对并“确认结论”，状态变为“测试不通过”，项目进入整改中。
10. 开发修复任务审批完成后，项目负责人点击“发起下一轮”，填写新阶段/版本。
11. 下一轮测试通过后，测试组长确认结论；项目测试门禁变为通过。

**预期结果**：完整留下任务快照、排期、活动、工时、批次、报告状态、结构化结论、整改任务和轮次历史。

**注意事项**：失败轮次不会自动批量打回所有开发任务。需要整改的内容必须落到明确的同项目开发任务。

### 15.2 示例：外部独立测试“示例合作方接口联调”

**适用角色**：测试工程师、测试组长、主测试负责人。

**前置条件**：已配置测试小组。

**操作步骤**：

1. 测试工程师点击“登记外部测试”，用文本填写外部项目名称和负责人。
2. 测试组长确认排期、指定主测并拆分活动。
3. 主测开始测试，参与人登记批次和工时，处理报告状态。
4. 主测提交结构化结论，测试组长退回一次并写明原因。
5. 主测修改后重新提交，测试组长确认结论。

**预期结果**：外部测试独立形成轮次和资源投入，不需要创建 Gather 项目，也不进入内部项目成本。

**注意事项**：外部负责人为普通文本，不应填账号凭据或非必要个人信息。

## 16. 常见问题排查

### 16.1 无法登录

1. 确认邮箱和密码输入正确，密码至少 6 位。
2. 新注册账号确认是否已完成邮箱验证。
3. 联系管理员确认账号是否停用。
4. 若页面显示“演示模式”，请确认你是否误入演示环境。
5. 不要把密码或报错中可能包含的凭据发到群聊或工单。

### 16.2 看不到菜单或操作按钮

1. 查看左下角系统角色。
2. 区分系统角色和业务身份：项目负责人、测试组长、主测都需要数据关系。
3. 检查当前对象状态是否允许操作，例如只有“测试中”才可记录执行批次。
4. 刷新页面重新加载权限与状态。
5. 仍有问题时，把页面名称、对象名称、当前状态和预期按钮提供给管理员；不要提供账号密码或浏览器 Cookie。

### 16.3 manager 无法创建项目

原因通常是当前用户没有担任任何小组组长。请管理员在“小组管理”中建立真实组长关系；单纯设置 `manager` 角色不够。

### 16.4 看不到“发起内部测试”或项目不在下拉框

逐项检查：

- 当前用户是否为项目负责人；
- 项目是否为“进行中”；
- 是否已有进行中的测试轮次；
- 是否已批准无需测试；
- 是否至少有一条已审批完成且未被通过轮次覆盖的开发任务；
- 搜索条件是否过滤了该项目。

### 16.5 提交测试结论失败

1. 确认操作者是主测试负责人，轮次为“测试中”。
2. 确认七项结构化结论全部非空；没有阻断也要填写“无”。
3. 确认所有必需报告已标记“已出具”或填写原因后标记“未出具”。
4. 内部项目不通过时确认已选择具体整改任务。
5. 若最终确认出现状态约束错误，请管理员确认数据库已执行 `0011_fix_test_conclusion_and_construction_summary.sql`。

### 16.6 任务无法提交或审批

1. 提交前确认任务为“进行中”、项目存在且项目负责人有效。
2. 逾期任务必须填写延期原因。
3. 审批按钮只对当前项目负责人显示。
4. 若负责人已停用，先在“项目管理”更换负责人；管理员确需代办时必须填写原因。

### 16.7 实际工时与预期不一致

- 普通开发任务：只累计“进行中”期间已关闭的工时段；当前尚未结束的工时段可能暂未进入汇总。
- 测试活动和测试建设：由授权人员手工“登记工时”。
- 挂起期间不计时。
- 多人并发工时直接累加，不按自然日去重。

### 16.8 建设详情显示异常汇总

请管理员确认数据库已执行 `0011`。该迁移补齐建设详情的任务数、完成数、计划工时和实际工时聚合。

### 16.9 通知没有跳转入口

当前通知面板主要用于提醒和已读管理。根据通知内容手工进入“任务管理”“项目管理”或“测试中心”，再用名称或状态筛选定位。

## 18. 术语表

| 术语 | 含义 |
| --- | --- |
| 系统角色 | `admin`、`manager`、`user`，决定菜单和通用管理能力 |
| 业务身份 | 由项目、团队、轮次等数据关系产生的职责，如项目负责人、测试组长、主测 |
| 项目负责人 | 项目字段指定的人，审批全部项目开发任务并负责项目级测试发起 |
| 测试组长 | 被标记为测试小组的小组组长，负责测试治理确认 |
| 主测试负责人/主测 | 测试组长在排期时指定的本轮主要执行责任人 |
| 测试计划 | 内部项目或外部独立测试的长期容器，可包含多个轮次 |
| 测试轮次 | 针对某阶段/版本的一次排期、执行和结论闭环 |
| 测试活动 | 测试组长将轮次拆给具体测试人员的计划工作单元 |
| 执行批次 | 某日、环境、构建版本和测试类型下的一次执行数据记录 |
| 结构化结论 | 测试范围、完成情况、问题、阻断、风险和发布建议等完整结论 |
| 测试门禁 | 项目完成前对测试通过或无需测试批准的要求 |
| 无需测试 | 项目负责人申请、测试组长批准后解除测试门禁的正式决定 |
| 测试建设 | 不关联项目的自动化框架、脚本、工具、环境、数据或平台建设 |
| 工时段 | 开发任务进入“进行中”到离开“进行中”的计时区间 |
| 实际投入 | 已闭合工时段或测试中心手工登记工时的累计值 |
| 延期完成 | 工作实际提交时间晚于截止日期，审批通过后的终态 |
| Reopen | 已关闭问题重新打开的数量 |
| RLS | 服务端行级权限；即使绕过前端按钮，也会限制越权数据操作 |
| 禅道 | 用例和 Bug 明细的外部唯一来源；Gather 保存汇总及链接 |

## 20. 当前差异与待业务确认项

### 20.1 已核实的代码/材料差异

1. “权限管理”页面中的经理说明仍写有“审批本小组项目下的任务”，但当前任务页面和数据库口径均明确：普通审批权只属于项目负责人。使用人员应以本手册和实际审批按钮为准；建议产品后续修正文案。
2. `docs/uat/FIRST-RUN-REPORT.md` 记录最终测试结论状态映射和建设详情汇总缺陷；当前仓库的 `0011_fix_test_conclusion_and_construction_summary.sql` 已提供修复，自动化用例也已按最终状态 `passed` 编写，但现有报告没有记录迁移部署后的完整 `full` 全绿结果。上线前仍应在目标环境执行迁移并完整复验。
3. 需求文档描述了“忘记密码”和重发验证邮件，但当前登录页没有对应按钮。本手册不把它写成可用功能，密码重置需联系管理员。
4. 通知数据库可能产生测试中心专用事件，但当前通知面板只为部分旧任务通知配置了中文模板；未知通知类型可能显示内部类型名。

### 20.2 仍需业务方补充确认

- 正式组织是否允许用户自助注册，还是统一由管理员创建/邀请。
- 账号密码重置的实际办理渠道和服务时限。
- 是否只允许一个测试小组；当前界面文案为“一个组织可配置测试小组”，但数据结构和部分逻辑可容纳多个测试小组，且无需测试通知会取最早创建的测试小组组长。
- 管理员异常代办的审批授权规范、需要留存的证明和定期审计责任人。
- 项目、任务和测试数据的删除/归档周期，以及误删后的恢复流程。
- 执行批次与禅道字段的组织统一口径，例如 Bug、Reopen、阻断和跳过如何计数。
- 测试报告“已出具”后的文件实际存放位置和命名规范；Gather 当前不上传或关联报告文件。
- 截图是否允许在指定 UAT 环境采集，以及可使用的脱敏账号和虚构数据集。
