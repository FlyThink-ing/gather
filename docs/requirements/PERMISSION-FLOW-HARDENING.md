# 权限、流程、统计与工时统一实现合同

- 状态：**已确认**
- 确认日期：2026-08-14
- 适用版本：需求 v2.19 及以后
- 关联章节：`gather-需求-v2.md` 第十九章、D33—D42

## 1. 合同目的与优先级

本文是权限与流程加固的实现、联调和验收合同。它不替代完整需求文档，但当旧章节、既有页面或历史迁移存在以下冲突时，以本文和需求第十九章为准：

* 前端按钮与 RLS/RPC 不一致；
* 默认列表、深链详情和统计数字的数据范围不一致；
* manager、组长、项目负责人和任务负责人的职责混用；
* 把“开发完成”误写成“项目完成”，造成测试流程循环；
* 计划、活动、资源视图使用不同工时真源。

任何实现不得以兼容旧客户端为由保留可绕过的新旧双入口。

## 2. 跨层不变量

每个对象和动作都必须同时满足四层规则：

| 层级 | 合同 |
| --- | --- |
| 可见 | 列表、搜索、统计只返回当前人员有权查看的对象 |
| 可达 | 详情 RPC、手工 URL、`focus`、项目/通知深链不得突破列表范围 |
| 可操作 | 前端按钮与 RLS/RPC 使用同一动作授权和状态门禁 |
| 可计数 | 卡片数字、项目指标、列表 `total` 使用相同授权集合和筛选谓词 |

必须成立：

```text
metric_count(actor, filters)
= list_total(actor, filters)
= count(detail_ids that actor can open)
```

客户端参数只能收窄服务端权限集合。`scope=all` 仅对 admin 表示全局；其他身份传入时不得扩权。`focus=<id>` 只定位已在允许集合中的任务。

## 3. 授权原语

实现可以使用 RLS、SQL 函数或 RPC，但必须形成等价的单一判断，不得由各页面自行拼接不同规则。

### 3.1 项目

`can_view_project(actor, project)`：满足任一条件：

* actor 是 admin；
* actor 是项目负责人；
* actor 管理项目所属小组；
* actor 是项目有效任务负责人或获授权测试参与人，只返回其工作所需摘要。

`can_edit_project_business(actor, project)`：项目负责人；admin 仅异常处置。允许字段限定为描述、计划开始/结束日期、测试说明等业务字段。

`can_change_project_governance(actor, project)`：admin，或管理项目所属小组的 manager。只允许通过独立动作修改 `team_id`、`owner_id`，必须审计。

`can_transition_project(actor, project, action)`：项目负责人执行正常暂停、恢复和完成；admin 强制动作必须填写原因。普通表单不得直接更新 `status`。

`can_delete_project` 与 `can_delete_task`：本轮始终为否。项目和任务不提供直接硬删除入口，admin/manager 也不得使用旧直接 `DELETE` 能力。异常数据处置须等待带原因、审计、关联完整性检查的归档或专用流程另行确认。

### 3.2 任务

`can_view_task(actor, task)`：满足任一条件：

* admin；
* task.developer_id 是 actor；
* task.project.owner_id 是 actor；
* task.developer_id 是 actor 所管理小组的有效成员；
* 测试活动/建设任务中 actor 是被分配人员或有对应测试管理权限。

manager 角色本身不构成全局查看条件。空小组不产生其他人员任务范围，仅有 `task.team_id` 而无有效成员关系不能作为查看他人任务的唯一依据。

`can_execute_task(actor, task)`：仅任务负责人，且任务为开发工作并处于当前动作允许状态。

`can_manage_task(actor, task)`：管理任务负责人所属小组的组长，仅允许通过专用动作改派负责人、调整计划日期或优先级；所有变更审计。

`can_approve_task(actor, task)`：任务为项目开发任务、状态为 `review`，且 actor 等于当前 `projects.owner_id`。admin 代办使用独立 RPC 并记录原因。

### 3.3 测试计划

`can_view_test_plan(actor, plan)`：满足任一条件：

* admin；
* 内部计划关联项目的当前项目负责人；
* 计划创建人；
* actor 是本计划主测试负责人、轮次参与人或活动参与人；
* actor 是该计划测试组的测试组长。

普通测试岗位不能仅凭职位查看全部计划。外部计划中的文本项目负责人不产生账号授权。

动作仍按职责分离：项目负责人发起内部测试；测试组长接单排期、分配资源并确认结论；主测试负责人提交结论；参与人执行活动和登记批次。

## 5. 项目与测试状态合同

### 5.1 术语

* **任务完成**：单个开发/修复任务已由项目负责人批准为 `done/delayed_done`。
* **开发就绪/可提测**：本轮固化范围非空，范围任务全部完成并有审批记录。
* **测试通过/待项目关闭**：最近有效测试轮次已由测试组长确认为通过，项目仍为 `active`。
* **项目完成/关闭**：项目负责人通过项目完成门禁后，`projects.status='completed'`。

### 5.2 状态机

```text
active + not_requested
  → 范围就绪
  → requested
  → scheduled/accepted
  → testing
  ├─→ failed/fixing → 修复任务完成并审批 → requested
  └─→ conclusion_pending → passed
                              → 项目完成门禁
                              → completed
```

无需测试：

```text
active + not_requested
  → no_test pending
  → 测试组长 approved
  → no_test_approved
  → 项目完成门禁
  → completed
```

### 5.3 门禁

| 动作 | 必须满足 | 必须阻止 |
| --- | --- | --- |
| 进入内部测试候选 | active；当前人员为项目负责人；范围非空；范围任务已审批完成；无活动轮次；未批准无需测试 | completed/paused；无合格范围；活动轮次存在；无需测试已批准 |
| 发起整项目测试 | 当前项目全部纳入范围的开发/修复任务就绪 | 仅任意一个任务完成但其余任务仍在办 |
| 发起阶段/版本测试 | 阶段/版本范围已显式定义并固化，范围内任务全部就绪 | 未定义范围时用零散已完成任务提前提测 |
| 确认测试通过 | 结构化结论完整；报告状态均已选择；过程数据完整；测试组长确认 | 主测试负责人提交后直接生效 |
| 正常完成项目 | 所有开发/修复任务完成；无 review；无活动测试；测试通过或无需测试已批准；无其他阻断 | 测试中、整改中、未测试、待审批或任务未完成 |

项目在开发、测试和整改期间始终保持 `active`。不得实现“先 completed 才允许测试”。

## 6. “待我审批”与任务入口合同

“待我审批”唯一谓词：

```text
task.status = 'review'
AND task.project_id IS NOT NULL
AND task.project.owner_id = current_developer_id
```

该集合与当前人的任务负责人、小组成员关系和全局角色无关。

* 工作台卡片、通知角标、任务管理预设和审批列表必须复用该谓词。
* 项目驾驶舱待审批数为该项目全部 `review` 任务；当前项目负责人点击后数量必须一致。
* 非项目负责人即使是 manager/组长也不得看到审批按钮或执行审批 RPC。

深链执行顺序固定为：

```text
actor allowed set
→ apply project/status/person/timing filters
→ apply focus locator
→ paginate and count
```

不得先按 URL 找到对象再跳过授权，也不得因项目入口自动设置全局 `scope=all`。

## 7. 统计合同

工作台任务卡：

| 指标 | 口径 | 目标入口 |
| --- | --- | --- |
| 总任务 | 当前人员工作范围内全部可见任务 | 任务管理对应工作范围 |
| 进行中 | 工作范围内 `in_progress` | 状态预设 |
| 测试中 | 当前人员可见且正在执行的测试活动/历史兼容测试 | 测试中预设 |
| 待我审批 | 第 6 节唯一谓词 | 待我审批预设 |
| 已完成 | `done` | 完成预设 |
| 延期完成 | `delayed_done` | 延期完成预设 |
| 逾期 | 未完成且超过截止日期 | 逾期预设 |

所有可点击卡片必须满足数字与列表 `total` 相等。Bug、Reopen、测试轮次等不属于任务集合的指标应进入测试详情/质量页，不得伪装成任务筛选。

## 8. 工时合同

### 8.1 实际投入

实际投入唯一真源为有效、未作废、已结束的工时明细/工作段。汇总数只计算，不直接写入。

```text
actual_hours = Σ valid ended work entries duration
```

进行中的计时段单独展示，不计入正式实际投入。日期范围统计按工时段与查询窗口的交集时长计算。

### 8.2 计划投入

正式计划投入唯一真源为测试活动按人员分配值：

```text
activity planned = Σ activity participant planned_hours
cycle planned = Σ activities planned
plan planned = Σ all cycles planned
```

轮次参与人字段用于角色/可见范围，计划工时必须由活动汇总生成或保持只读，不能与活动计划重复累加。未拆活动时只显示“预排计划”。

测试建设的正式计划投入唯一真源为 `test_construction_tasks`：

```text
construction task planned = test_construction_tasks.planned_hours，归属 owner_id
construction work planned = Σ construction tasks planned_hours
resource construction planned = Σ visible construction tasks planned_hours by owner/date range
```

`test_construction_participants` 只表达工作级参与关系和预排范围，不作为正式计划工时汇总来源，也不得与建设任务计划重复累加。

### 8.3 修正与锁定

* 进行中：普通登记人仅可修改/作废本人创建且未锁定的 `manual` 手工明细，必须填写原因并审计。
* 自动明细：`automatic` 对普通人员只读；仅对应测试组长或 admin 可按异常修正流程处理，必须填写原因并记录 before/after，不能无痕覆盖。
* 终态：测试结论已确认或建设已完成后，`manual` 和 `automatic` 均锁定；仅对应测试组长或 admin 可按异常修正流程处理并留痕。

### 8.4 展示范围

测试计划卡默认展示全计划全部轮次累计，字段标签必须明确为“全计划累计计划投入”“全计划累计实际投入”。轮次详情只展示本轮。相同筛选范围下：

```text
活动合计 = 轮次合计 = 计划累计 = 资源汇总对应来源合计
建设任务计划合计 = 建设详情计划投入 = 资源汇总测试建设计划投入
```

## 9. UI 与安全验收场景

至少准备以下账号和数据：admin；无管理小组的 manager；有组员的组长；普通任务负责人；跨组项目负责人；测试组长；主测试负责人；普通测试参与人。

### 9.1 P0 场景

1. 无小组 manager 修改 URL 为 `scope=all`，只能看到本人任务；直接 RPC 也不能返回他人任务。
2. manager 对他人任务的普通 UPDATE、开始、暂停、提交均被拒；本组改派/调计划只能走管理动作并有审计。
3. 跨组项目负责人有 1 条 `review`：工作台“待我审批”=1，点击后 `total=1`，详情可达并能审批。
4. 非项目负责人从项目指标、通知或手工 `focus` 打开无权任务，不能获得任务详情。
5. 项目负责人可以编辑描述/计划日期，不能改 `team_id`、`owner_id`、`status`；直接请求同样被拒。
6. admin、manager 和普通用户均看不到项目/任务直接删除按钮；直接 `DELETE` 被后端拒绝，且不能用旧删除能力代替尚未确认的归档流程。

### 9.2 P1 流程与测试场景

1. active 项目的整项目范围全部任务审批完成后可提测；项目无需先 completed。
2. 尚有范围内任务在办时不能提测；明确阶段/版本范围时只检查固化范围。
3. 测试通过后项目显示“待项目关闭”，仍为 active；完成门禁通过后才变 completed。
4. 项目负责人能从项目详情和测试中心查看关联计划，但看不到排期、执行、结论确认按钮。
5. 普通测试人员只能看到本人参与计划，不能仅凭测试职位浏览全部计划。

### 9.3 P1 工时场景

1. 登记 2h 与 3h 后各层合计 5h；把 3h 修正为 2.5h 后各层同步为 4.5h，且有审计。
2. 终态修正未经测试组长确认不能生效。
3. 跨日期筛选只计算交集；进行中段单列，不混入正式实际。
4. 计划卡明确显示“全计划累计”，各轮相加与资源汇总一致。
5. 测试建设任务的 `planned_hours` 按 `owner_id` 汇总后，与建设详情和资源汇总中的建设计划投入完全一致；参与人预排值不重复计入。

### 9.4 P2 展示场景

1. 活动卡计划、实际投入分栏，数值和单位不换行。
2. 125% 缩放和窄屏下字段纵向排列，无横向溢出。
3. 无数据使用“未录入/未设置”，不得以 0 伪造。

## 10. 交付优先级

| 优先级 | 范围 | 完成标准 |
| --- | --- | --- |
| P0 | 可见集合、深链、项目字段、manager 他人任务、项目/任务硬删除关闭、待我审批、统计一致 | 权限和审批相关跨层场景全部通过 |
| P1 | 开发就绪到项目关闭、测试计划可见性、可点击入口 | 不存在状态循环，角色查看/动作边界一致 |
| P1 | 工时明细修正、审计、计划与资源聚合 | 同源同范围汇总完全一致 |
| P2 | 工时卡片布局、空状态、响应式 | 桌面和窄屏视觉验收通过 |

## 11. 非目标

本轮不改变已确认的项目负责人逐项审批原则，不恢复单任务提测，不新增个人绩效排名，不以关闭 RLS 或前端隐藏替代数据库权限，也不要求外部项目负责人注册系统。本轮不设计软删除、归档或异常数据清理流程；在该流程另行确认前，项目和任务继续禁止直接硬删除。
